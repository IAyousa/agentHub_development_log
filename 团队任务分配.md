## 2. 核心设计决策

> 以下决策经过团队讨论确认，所有成员开发时应以此为基准。

### 2.1 单聊 vs 群聊 — 方案 A：两种 UI，共享消息引擎

**当前阶段只做单聊（direct），群聊（group）推迟到 P2。**

| 模式 | type 值   | 参与者               | 前端 UI                            | 当前状态   |
| -- | -------- | ----------------- | -------------------------------- | ------ |
| 单聊 | `direct` | 1 个用户 + N 个 Agent | **ChatView**（聊天气泡布局）             | P0 开发中 |
| 群聊 | `group`  | M 个用户 + N 个 Agent | **OfficeView**（SVG 办公室 + 底部聊天抽屉 ✅） | P0 已完成  |

**关键设计原则**：ChatView 和 OfficeView 是两套"皮肤"，内核共用同一套消息引擎（Pinia store + WebSocket client + ChatMessage 组件）。消息逻辑只写一遍。

### 2.2 中间栏展示内容

中间栏（ChatList）展示的是**用户的会话列表**，而非 Agent 列表。每个会话可包含多个 Agent（通过 `conv_agents` 关联表维护）。

```
中间栏（会话列表）
├── 🏠 默认会话      ← direct，包含 Orchestrator + Coder
├── 📁 前端开发任务   ← direct，包含 Coder
└── 📁 代码审查      ← direct，包含 Claude Code
```

点击会话后，根据 `conversation.type` 自动路由：

- `type=direct` → ChatView（聊天气泡）
- `type=group` → OfficeView（SVG 办公室 + 底部聊天抽屉，P2 实现）

### 2.3 办公室聊天面板 — 方式 2：底部抽屉

OfficeView 的聊天面板采用底部抽屉式布局，保留 SVG 办公室场景的沉浸感：

```
┌──────┬──────────────────────────────────────────────┐
│ 导航  │      SVG 办公室场景（占大部分区域）            │
│      │   👤 Coder    👤 Designer    👤 你           │
│      │        🪑              🪑              🪑     │
│      ├──────────────────────────────────────────────┤
│      │  聊天面板（可折叠/展开）                        │
│      │  Claude: 我来完成这个前端任务                    │
│      │  Codex: 代码已经生成好了                        │
│      │  ┌──────────────────────────────────────┐    │
│      │  │ 输入消息...                           │    │
│      │  └──────────────────────────────────────┘    │
└──────┴──────────────────────────────────────────────┘
```

### 2.4 Agent 指派机制 — Orchestrator 调度

Agent 之间的协作调度完全是 **Python Agent Service 层**的内部逻辑，前端不感知任务拆分过程。

```
用户发消息
  → Orchestrator 分析需求，自动拆解子任务
    → 子任务 1：派给 Coder（代码生成）
    → 子任务 2：派给 Designer（UI 设计）
  → 汇总结果，流式返回前端
```

前端只需根据 WebSocket 推送中的 `agentId` 字段渲染不同 Agent 的头像和名称。发送消息时用户无需手动选择 Agent，Orchestrator 自动判断。

### 2.5 CORS 配置策略

| 阶段   | 方案                             | 说明                       |
| ---- | ------------------------------ | ------------------------ |
| 开发阶段 | CorsConfig + `application.yml` | 从配置文件读取允许的源地址，不硬编码       |
| 部署阶段 | Nginx 反向代理                     | 统一入口、无跨域问题、可加 HTTPS/gzip |

~~已实现~~：使用 `CorsFilter` Bean 而非 `WebMvcConfigurer`，覆盖 Servlet Filter 层全路径。

### 2.6 数据模型扩展说明

群聊（group）需要新增 `conversation_members` 关联表（用户 ↔ 会话多对多），并在 `conversations` 表增加 `description`、`theme`、`max_members` 字段。**当前 P0 阶段不建这些，仅** **`type`** **字段预留值** **`group`。** 前排 `conv_agents` 表（会话 ↔ Agent 多对多）已在单聊中投入使用。

**核心链路** (成员 A 负责实现，也是整个系统的核心数据流):

```
用户发消息 → WebSocketController.handleUserMessage()
  → MessageService.save()              // 保存用户消息到数据库
  → context = content.trim()           // 仅当前消息（CLI --continue 管理历史）
  → AgentGatewayService.sendToAgent()  // HTTP POST + SSE 到 Python
  → Python _session_tracker 判断首轮/后续 → adapter.chat_stream(is_first_message)
  → SSE 逐 token → STOMP 推送到前端
  // 推送时携带 agentId，前端据此显示不同 Agent 头像
```

> **注意**：当前 P0 阶段所有会话的 `type` 均为 `direct`（单聊）。群聊（group）的 ConversationMember 管理推迟到 P2。

**核心链路** (成员 D 负责实现):

```
FastAPI 收到 POST /api/agent/chat
  → orchestrator.route(message, history)
    → adapter_factory.get_adapter(agent_type)
    → adapter.chat(message, history, system_prompt)
    → async for token in llm_stream:
        yield f"data: {json.dumps({'token': token, 'finish': False, 'agentId': '...', 'agentName': '...'})}\n\n"
```

**SSE 响应格式**（每行一条 JSON，对照 API 文档 4.2 节）:

```
data: {"token": "我", "finish": false, "agentId": "agent_claude_001", "agentName": "Claude Code"}

data: {"token": "来", "finish": false, "agentId": "agent_claude_001", "agentName": "Claude Code"}

...

data: {"token": "", "finish": true, "messageId": "msg_456"}
```

> **agentId/agentName 的作用**：当 Orchestrator 切换调用的 Agent 时（如从 Coder 切到 Designer），后续 SSE chunk 中的 agentId/agentName 随之变化，Spring Boot 层据此推送 `agent_switch` 事件给前端。前端据此切换消息头像和发送者名称。

## 6. WebSocket 消息格式约定

> 格式与 [API 契约定义与通信协议规范](./API%20契约定义与通信协议规范.md) 第 3 节保持一致，以下为开发要点摘要。

### 前端 → 后端 (发送消息)

**Destination**: `/app/chat.send`

```json
{
  "conversationId": "conv_abc123",
  "content": "帮我写一个 React 组件"
}
```

> **仅传 conversationId + content**。不再传 agentType 和 systemPrompt，Agent 调度由 Orchestrator 自动完成。

### 后端 → 前端 (接收消息)

**Subscribe**: `/topic/conversation.{conversationId}`

**流式 token**：

```json
{
  "content": "好的",
  "isComplete": false,
  "agentId": "agent_claude_001",
  "agentName": "Claude Code",
  "messageType": "text"
}
```

**消息结束**：

```json
{
  "content": "完整回复内容...",
  "isComplete": true,
  "agentId": "agent_claude_001",
  "agentName": "Claude Code",
  "messageType": "text",
  "messageId": "msg_002"
}
```

**Agent 切换通知**（Orchestrator 切换 Agent 时推送）：

```json
{
  "type": "agent_switch",
  "agentId": "agent_codex_001",
  "agentName": "Codex"
}
```

**字段说明**：

| 字段          | 类型      | 说明                                         |
| ----------- | ------- | ------------------------------------------ |
| content     | string  | 流式时为 token 片段，isComplete=true 时为完整消息       |
| isComplete  | boolean | true 表示本条消息结束                              |
| agentId     | string  | 发送此消息的 Agent ID，前端据此切换头像和名称                |
| agentName   | string  | Agent 显示名称                                 |
| messageType | string  | text / code / diff / preview\_card / error |
| messageId   | string  | 消息 ID（isComplete=true 时返回）                 |
| type        | string  | `"agent_switch"` 时表示 Agent 切换事件            |
